### Phase 9.5: Failure-mode smoke

NOT RUN as a live test, but exercised via static reasoning per
the preflight code:

- **Missing venv**: `existsSync` returns false; `run-bridge.mjs` calls
  `fatal()` with the path and the fix instruction, exit 1.
- **Missing `.env`**: `checkEnv` records a FAIL with the exact path and

- **macOS**: not directly tested, but the script avoids macOS pitfalls:

  Linux code path.
- **Windows-native**: explicitly refused with a pointer to WSL2.

## 8. Notable design choices

- **Source `.env` in run-bridge**: the wrapper parses `~/.hermes/.env`
  and merges it into the child's environment before spawning Python.
  This matches what the legacy `bridge/run.sh` did via `set -a; source
  ...; set +a`. Without it, plugin handlers that need other secrets
  (provider tokens, etc.) would receive an incomplete env, even though
  the bridge itself only requires `API_SERVER_KEY`. The parser handles
  the simple `KEY=value` plus optional matching outer quotes; comment
  lines and blank lines are skipped. Verified the on-disk file uses
  only this subset (no `export`, no command substitution).
- **`PYTHONUNBUFFERED=1`**: forced on the child so concurrently's
  prefix-multiplexed output flushes line-by-line. Without this the
  bridge's startup logs would only appear after the first `\n` flush
  inside the buffer, which feels like a hang.
- **Re-raise the exit signal on self**: `process.kill(process.pid,
  signal)` after the child exits via signal. This produces the
  conventional 128 + signal exit code that wrapper scripts are expected
  to surface, instead of silently translating to exit 0.
- **`postinstall` not used**: tempting to wire `npm install` at the
  root to chain `npm install` in `web/`, but that hides the slow step
  in every root-level `npm install` and surprises people when they're
  just adding a top-level dep. `npm run setup` is explicit.
- **Workspaces not used**: npm workspaces would hoist `web/node_modules`
  to the root and break the existing Vite resolution. Out of scope.

## 9. Known limitations

- **Windows-native unsupported.** The Hermes plugin uses Unix paths
  internally (`~/.hermes/...`, POSIX signal handling). WSL2 is the
  supported workaround.
- **Asset server port hardcoded.** `bridge/server.py:137` hardcodes
  `port=9120` with no env override. The preflight checks the same
  hardcoded value. If we ever want to relocate it, we need to add a
  `SPRITE_ASSET_PORT` env var to the bridge first.
- **Hermes Agent install is external.** Preflight diagnoses a missing
  venv but cannot install Hermes; the user must do that step out of
  band. Unavoidable: Hermes is its own project with its own install
  flow.
- **`.env.example` to `.env` copy is a no-op for the bridge.** The
  bridge reads `~/.hermes/.env`, not the repo's `.env`. The repo
  `.env` exists only for surfacing the optional override knobs
  (`HERMES_HOME`, `SPRITE_BRIDGE_HOST`, etc.); developers who do not
  set any overrides never need it. The setup script copies it anyway
  so the file shows up in `ls` as a discoverability hint.
- **No live `npm run dev` exercise.** Phase 9.4 was deferred because
  the running stack would conflict on ports. The static checks are
  complete; the wrapper is small enough to inspect end-to-end.
